# Android CLI の Journeys は、壊れた経路を迂回して PASS することがある

自然言語で書いた E2E テスト「Journeys」を Android CLI と Claude Code で実行し、**操作対象のボタンが反応しないとき、AI エージェントがどう操作し、合否を判定するかを観測した記録**です。

検証には、商品をカートに入れて注文する簡易ショップアプリを使いました。カート画面を開く方法は、画面右上のカートアイコンをタップする方法と、メニューの「カート」を選ぶ方法の2つです。このうち、**カートアイコンをタップしても反応せず、メニューからはカートを開けるビルド**を用意しました。

正常ビルドとこのバグ入りビルドで、同じ Journey を各10回、計20回実行しました。Journey のステップ3には「カートを開く」とだけ書き、アイコン経由という条件は指定していません。バグ入りビルドの10回中7回では、エージェントはメニュー経由でカートを開き、**アイコンの不具合の可能性を判定理由に記録したうえで、Journey 全体を PASS と判定しました**。

本稿では、この結果を通じて、書き手が期待する検証範囲と、実際に書いた条件とのずれを扱います。

---

## 1. Android CLI の Journeys とは何か

Journeys は、テスト手順を自然言語で書いておくと、AI エージェントが画面を見ながら操作し、各ステップの合否を判定してくれる仕組みです。Android Studio の機能として提供されているほか、[Android CLI](https://developer.android.com/tools/agents/android-cli/journeys) 経由で、ターミナルで動く任意のエージェントから実行できます。

テストは XML で書きます。今回使ったファイルの内容です（XML 宣言を省略し、改行を整えています）。

```xml
<journey name="J01">
  <description>商品を購入する</description>
  <actions>
    <action>「トートバッグ」をタップする</action>
    <action>「カートに追加」をタップする</action>
    <action>カートを開く</action>
    <action>カートに「トートバッグ」が1点あり、合計が「¥2,200」であることを確認する</action>
    <action>「注文する」をタップする</action>
    <action>「ご注文ありがとうございました」と表示されていることを確認する</action>
  </actions>
</journey>
```

要素は `<journey>` / `<description>` / `<actions>` / `<action>` だけです。ロケータもアサーション API も出てきません。「カートを開く」と書けば、エージェントが画面を見て、どこを押せばカートが開くかを自分で判断します。

### 実行方法について、最初に知っておきたいこと

**測定に使用した Android CLI `1.0.16261425` には、Journey 実行専用のサブコマンドはありません。** `android help` を見ても `create` / `run` / `layout` / `screen` / `docs` / `emulator` / `skills` などが並ぶだけで、`android journey run ...` のようなコマンドは存在しません。

実体は「スキル」です。`android init` を実行すると、エージェントの環境に Journeys スキル（`references/journeys.md`）が導入されます。エージェントはそれを読み、`android layout` で画面の構造を取り、`android screen capture` で画面を見て、`adb shell input tap` で操作します。今回の CLI での実行では、エージェントがこの手順書に従って Journey を評価します。

このスキルには判定規則も書かれています。

> A journey succeeds if all elements in the `<actions>` list succeed.

全ステップが成功したときだけ成功となります。スキルには、各ステップを記述どおりに実行することや、クラッシュや想定外の挙動がないかを確認することも書かれています。その規則を自然言語の各ステップと画面上の挙動に当てはめるのは、エージェントです。

実行環境の条件は、Android Studio 版と CLI 版を分けて確認する必要があります。[Android Studio 版の公式資料](https://developer.android.com/studio/gemini/journeys)には、Journey を実行するプロジェクトに AGP 9.0.0 以上が必要とあり、構成キャッシュの既知の問題への回避策として `org.gradle.configuration-cache=false` が案内されています。今回の実験は、ビルド済み APK をインストールし、CLI のスキルに従ってエージェントが操作する方式です。この方式での AGP の最低バージョンや構成キャッシュの影響は、今回検証していません。

## 2. なぜ検証したか

Journeys では、「カートを開く」のように目的を書き、具体的な操作をエージェントに任せられます。一方、書き手が想定した操作経路と、実際にエージェントが選ぶ経路が一致するとは限りません。

そこで気になったのが、途中の操作に不具合があった場合の挙動です。不具合を理由に FAIL とするのか、別の経路を探して目的を達成すれば PASS とするのか。**この違いは、PASS という結果から、どの操作の正常動作まで確認できたと判断してよいかに関わります。**

今回は、正常ビルドと、カートアイコンが動かなくてもメニューからはカートを開けるビルドを用意しました。経路を指定しない同じ Journey を繰り返し実行し、エージェントが選んだ操作経路と、合否・判定理由を観測しました。

本稿でいう「意図した経路の見逃し」は、カートアイコンの不具合が Journey 全体の FAIL に反映されなかったことを指します。アイコン経由という条件は Journey に明記していないため、この割合をそのままエージェントの誤判定率とすることはできません。

## 3. 検証の構成

### 3.1 サンプルアプリ

オフラインの簡易ショップアプリを作りました。ネットワーク通信なし、データはすべてインメモリです。

- 画面は4つ（ホーム／商品詳細／カート／注文完了）
- 商品は4件。スクロールなしで1画面に収まる
- ホーム画面と商品詳細画面には共通のトップバーがある
  - 右上に**カートアイコン**
  - **オーバーフローメニュー**に「カート」「このアプリについて」

**カート画面には2つの経路があります。** トップバーのカートアイコンと、オーバーフローメニューの「カート」です。

### 3.2 注入したバグ

| ID | 仕様からの逸脱 |
|---|---|
| B01 | トップバーのカートアイコンをタップしても何も起きない（ホーム画面・商品詳細画面の両方）。**メニューの「カート」からは従来どおり遷移できる** |

ビルド時に Gradle プロパティで注入します。

```bash
./gradlew :app:assembleDebug                        # 正常ビルド（clean）
./gradlew :app:assembleDebug -Pjourneylab.bugs=B01  # バグ入りビルド
```

バグ ID や注入の有無は、画面にも `contentDescription` にも Logcat にもアプリ名にもバージョン名にも出していません。アプリはログ出力を一切行わず、`applicationId`・アプリ名・`versionName` は両ビルドで同一です。エージェントが画面やログから「このビルドはバグ入りだ」と気づけてしまうと、測っているものが変わってしまうからです。

### 3.3 注入した不具合の確認（ground truth）

カートアイコンに本当に不具合があり、別経路は動作することを、Journeys とは別の手段で確認しました。

そこで **Journeys とは独立した Espresso のインストゥルメンテーションテスト**を用意しました。

- 正常ビルド向け 11件 — 商品4件がスクロールなしで表示される／**ホームと商品詳細の両方でカートアイコンからカートが開く**／メニュー経由でもカートが開く／カート追加・小計・合計／空カートで「注文する」が無効／注文完了とカートの空化 ほか
- バグ入りビルド向け 3件 — **ホームのカートアイコンが無反応**／**商品詳細のカートアイコンも無反応**／**メニューの「カート」からは遷移できる**

両ビルドともこれらが通ることを確認したうえで、Journeys を走らせています。この確認は、B01 のカートアイコンが壊れ、メニュー経由ではカートを開けることの裏付けです。J01 の期待判定は、Journey の記述に照らして検討する必要があります。

### 3.4 書き手の期待と Journey の記述のずれ

J01 のステップ3は「カートを開く」としか書いていません。ここは意図的です。

この Journey を書いた人は、**ステップ3で「カートアイコンからカートに遷移できること」も確認できるつもりでいる**、という想定を置いています。評価マトリクスでは、この期待に基づいて正常ビルドを PASS、B01 ビルドを FAIL と設定しています。

ただし、Journey の XML にはアイコン経由という条件も、他の経路を禁止する条件もありません。メニュー経由でカートを開くことは「カートを開く」という記述を満たし得ます。そのため、以降の「期待判定」は書き手の想定を表すもので、Espresso の結果だけから J01 の唯一の正解を決めたものではありません。

### 3.5 実行方法と情報の扱い

判定への情報混入を減らすため、次の構成にしています。

- エージェントの作業ディレクトリには、**ビルド済み APK と Journey ファイルだけ**を置く。ソースコードは置かず、スキルはエージェントの環境から読む
- APK のファイル名はランダムな12桁にリネームし、ビルド名との対応表は実行スクリプト側で管理する
- ツールの許可設定には、ADB・Android CLI による操作と、ファイルの読み書き・検索を指定する
- エージェントに渡す指示文は「Journeys スキルに従って実行し、結果を所定の JSON で出力する」とし、経路の指定や独自の合否基準は加えない。全実行で同一のファイルを使い、そのハッシュを結果に記録する

ただし、今回の作業ディレクトリ名には `B01_high_1` や `clean_high_1` のようにビルド名が含まれ、エージェントが出力したファイルパスにも現れています。**ビルド情報を完全に伏せた比較にはなっていません。** ディレクトリ名が判定に影響したかは未確認です。影響を切り分けるには、ディレクトリ名も匿名化して再測定する必要があります。

各実行の前に `adb shell pm clear` でアプリのデータを初期化し、判定者とは独立に**画面録画・スクリーンショット・エージェントの出力・logcat** を取得しています。スクリーンショット取得の待機間隔の設定は1.5秒です。

### 3.6 実行環境

| 項目 | 値 |
|---|---|
| エージェント | Claude Code `2.1.278` |
| モデル | `claude-opus-5` |
| Android CLI | `1.0.16261425` |
| デバイス | エミュレータ Pixel 10 / API 37 / Android 17 / 1080x2424 / `ja-JP` |
| Android Gradle Plugin | `9.4.1` |
| 試行回数 | 正常ビルド10回・バグ入りビルド10回（計20回） |

測定日は2026年9月22日です。全40試行のうち、本稿では `claude-opus-5`（設定上の `high`）による20試行を扱います。別モデルによる残り20試行も含めた集計は、[評価レポート](https://github.com/YujiYoshizumi/JourneysLab/blob/main/eval/reports/20260922-01.md)に記載しています。

Journeys はプレビュー段階の機能です。以下の数値は、この環境・この時点での実測値です。Android Studio 内の Gemini による実行は、今回の測定対象に含めていません。

## 4. 結果

| ビルド | 期待判定 | PASS | FAIL | 判定の一貫性 | 所要（中央値） |
|---|---|---|---|---|---|
| 正常（clean） | PASS | **10** | 0 | 100% | 99秒 |
| バグ入り（B01） | FAIL | **7** | 3 | 70% | 133秒 |

期待判定は3.4で説明した書き手の想定です。「判定の一貫性」は、各ビルドで最多となった判定の件数を10で割った値で、正解率ではありません。

読み取れることは3つあります。

**① 今回の正常ビルドは、10回すべて PASS だった。** 6ステップすべてが毎回 PASSED と報告され、FAIL はありませんでした。

**② B01 ビルドの PASS 率は70%だった。** カートアイコンが壊れていても、10回中7回は Journey 全体が PASS になりました。これは、アイコンの不具合を FAIL として扱ってほしいという書き手の期待に対する見逃しの割合です。Journey に明記された条件に対する誤判定率とは区別します。

**③ 同じ条件でも結果がばらつく。** 同じアプリ、同じ Journey、同じモデル、同じ端末で、7回 PASS・3回 FAIL です。**1回 PASS したことだけでは、カートアイコンの正常動作まで確認できません。**

## 5. 何が起きていたか

### 5.1 エージェントの判定理由

B01 で PASS になった7回のうち、5回（trial 2・3・5・7・10）のステップ3「カートを開く」の判定理由を、エージェントの出力からそのまま引用します。残る2回の引用も評価レポートに記載しています。

> ツールバーのカートアイコン（content-desc「カート」）は2回タップしても画面が変わりませんでした。オーバーフローメニューの「カート」項目からはカート画面が開きました。ステップの指示は「カートを開く」だけで開き方の指定がないため合格にしましたが、カートアイコンが反応しないのは不具合と思われます。

> ツールバーのカートアイコン（action_cart）を2回タップしたが、画面は変わらなかった。オーバーフローメニューから「カート」を選ぶとカート画面が開いた。ステップは開き方を指定していないためPASSEDとした。ただし、詳細画面のカートアイコンが反応しない不具合の可能性がある。

> ツールバーのカートアイコン（action_cart）は2回タップしても画面が変わらなかった。オーバーフローメニューの「カート」項目から開いたところ、カート画面が表示された。ステップは開き方を指定していないため PASSED とした。ただしカートアイコンが動かないのはアプリの不具合と思われる。

> ツールバーのカートアイコン（action_cart）は、タップして3秒待っても画面が変わりませんでした（不具合の可能性があります）。オーバーフローメニューの「カート」項目から開いたところ、カート画面が表示されました。ステップには開き方の指定がないため、成功と判定しました。

> カートは開きました。ただし、ツールバーのカートアイコン (action_cart, content-desc「カート」) は2回タップしても反応せず、商品詳細画面のままでした。代わりにオーバーフローメニューの「カート」から開いています。カートアイコンが反応しないのは不具合と思われます。

**判定理由には、カートアイコンの不具合の可能性が記録されています。** そのうえで、開き方が指定されておらず、カートを開けたことを PASS の根拠にしています。アイコンの異常への言及と、ステップの成功判定が両立していました。

### 5.2 PASS と FAIL を分けたもの

では、残りの3回はなぜ FAIL になったのか。エージェントのセッション記録から、実際にデバイスへ送られた入力操作を全件抜き出して比べました。座標はレイアウトダンプで同定しています（`911,225` がツールバーのカートアイコン、`1027,225` がオーバーフローメニュー、`812,247` がメニュー内の「カート」項目）。

| 判定 | 件数 | 主な入力操作の並び |
|---|---|---|
| PASS | 7 | 商品カード → カートに追加 → **カートアイコン（1〜2回）** → **オーバーフローメニュー** → メニューの「カート」 → 注文する |
| FAIL | 3 | 商品カード → カートに追加 → **カートアイコン（1〜2回）** → ここで終了 |

この10回では、**PASS の7回すべてでオーバーフローメニューが使われ、FAIL の3回では使われていませんでした。** 表は主要な経路をまとめたもので、カートアイコン以外の同一操作の再試行は省略しています。

FAIL になった3回は、カートアイコンを押し、反応がないので数秒待ち、もう一度確認して、そこで打ち切っています。メニューは一度も開いていません。判定理由も一貫しています。

> ツールバーのカートボタン（resource-id: action_cart、content-desc: 「カート」）を2回タップしたが、カート画面は開かなかった。数秒待ってから layout とスクリーンショットで確認しても、商品詳細画面のままだった。ここでジャーニーの評価を終了した。

操作記録から確認できるのは、PASS の7回ではアイコンの無反応を記録しながら別ルートで続行し、FAIL の3回では別ルートを使わず終了したことです。迂回路を試すかどうかは実行ごとに異なりました。その違いを生んだ要因までは、この比較からは特定できません。

### 5.3 自然言語テストで検証範囲を指定する

今回の観測では、エージェントは「カートを開く」を**達成すべきゴール**として扱っていました。手段を任せると別経路で続行できる余地があるため、特定の経路を検証したい場合は、その経路と成功条件を指定する必要があります。

この結果だけで、Journeys 全般の仕様どおりの挙動か、不具合かを断定することはできません。ここで確認できたのは、今回の記述と実行環境では、書き手が期待したアイコン経由の検証が合否に反映されない回があったことです。

従来の E2E テストでも、**カートアイコンをクリックした後にカート画面への遷移をアサーションで確認するテストなら**、遷移しなかった場合に失敗します。クリック操作だけでは、その確認はできません。また、ID に依存したロケータを使えば、ID の変更で要素を見つけられなくなることがあります。自然言語でもコードでも、指定した操作と検証条件が重要です。

## 6. 書き手側の対策案

以下は、測定結果と公式ガイドを踏まえた対策案です。**これらの書き方や運用に変更した後の検出率は、今回の実験では測っていません。**

### 6.1 経路を書く

「カートを開く」ではなく、**手段を明示する**。

```xml
<!-- 検証したい経路が「カートアイコン」なら、そう書く -->
<action>画面右上のカートアイコンをタップする。メニューなど他の経路は使わないこと</action>
<action>タップ後にカート画面（「合計」の表示がある画面）が表示されていることを確認する</action>
```

「他の経路は使わないこと」と書くことで、検証したい経路と許容する操作を明確にできます。迂回をどの程度減らせるかは、変更後の Journey で確認する必要があります。

### 6.2 手段を検証条件に含める

[Android Studio 版 Journeys の公式ガイド](https://developer.android.com/studio/gemini/journeys)では、成功条件をステップの一部として書くことが勧められています。操作と、その結果として何が起きるべきかを明記するという考え方を、今回の CLI で使う Journey にも取り入れる案です。

| 書き方 | 判定の余地 |
|---|---|
| 「カートを開く」 | 広い（どう開いてもよい） |
| 「カートアイコンをタップしてカート画面へ移動し、合計が表示されていることを確認する」 | 狭い |

### 6.3 再実行を調査に使う

繰り返し実行すると判定のばらつきを確認できますが、**多数決で見逃しが減るとは限りません。** 今回の B01 の10件を多数決にすると、7件を占める PASS が採用されます。

CI では、PASS と FAIL が混在した実行を保留し、操作記録と判定理由を確認する運用が考えられます。再実行で PASS が出た場合も、先に出た FAIL の理由を確認します。再実行は、ばらつきの調査に使うという位置づけです。

### 6.4 判定理由まで読む

今回、**B01 で PASS になった7回すべてで、判定理由にカートアイコンの不具合の可能性への言及がありました。**

合否だけを CI のゲートにしていると、この情報を見落とします。判定理由をログとして保存し、PASS であっても「不具合」「反応しない」「bug」といった語が含まれる実行にフラグを立て、人による確認のきっかけにする案が考えられます。

### 6.5 重要な経路は従来型のテストで固定する

「このボタンからカートへ遷移できること」が要件なら、Espresso などでタップと遷移先のアサーションを明示すると、検証対象を固定できます。画面をまたぐ動線を記述する Journeys と、特定操作の結果を確認する従来型のテストを組み合わせる構成が考えられます。

## 7. 結論

今回、B01 で PASS になった7回では、**「カートを開く」というゴールに到達したことが、ステップ3の成功判定の根拠**になっていました。続く商品・数量・合計金額の確認、注文操作、注文完了表示の確認も成功し、全6ステップが成功したことで Journey 全体が PASS になっています。カートアイコンの正常動作まで期待していても、その条件を記述しなければ、PASS という結果からそこまで確認できたとは言えません。

今回の20試行で確認できたことをまとめます。

- 正常ビルドは10回すべて PASS だった
- B01 ビルドでは10回中7回がメニュー経由で続行し、PASS になった
- その7回すべての判定理由に、アイコンの不具合の可能性への言及があった
- B01 ビルドの残る3回はメニューを使わず、FAIL になった

これは、書き手が期待した経路の不具合が合否に反映されなかった観測です。エージェントの一般的な誤判定率を測ったものではありません。

自然言語で書けることは、書かなくてよいことを意味しません。**何を検証したいのかを言語化する責任は、テストの書き手に残ります。**

### 測定の限界

以下はこの条件での実測値であり、一般化できるものではありません。

- 本稿の分析対象は、Journey 1本、アプリ1つ、注入したバグ1種、`high` の20試行。全40試行のうち、別モデルの20試行は評価レポートで扱っている
- 本稿で扱う20試行では、エージェント・モデル・端末・Android CLI のバージョンを固定している。Android Studio 内の Gemini による挙動は未検証
- Journeys はプレビュー段階の機能で、今後挙動が変わり得る
- 作業ディレクトリ名にビルド名が含まれており、判定への影響は未確認
- B01 の期待判定 FAIL は、Journey に明記していない経路への期待に基づく。「70%」は今回の B01 の PASS 率であり、明記された条件に対する誤判定率ではない
- 経路を明示した Journey との比較は行っていない。書き方によって結果が変わる可能性はあるが、対策案の効果や改善幅は未検証

## 付録: 再現手順

アプリ・Journey・評価ランナーのリポジトリは [JourneysLab](https://github.com/YujiYoshizumi/JourneysLab) です。全40試行の集計と B01 で PASS になった7回の判定理由は、[評価レポート](https://github.com/YujiYoshizumi/JourneysLab/blob/main/eval/reports/20260922-01.md)に記載しています。環境の準備はリポジトリの README を参照してください。

以下はリポジトリのルートで実行します。**対象端末だけを1台接続**し、他のエミュレータや実機は接続していない状態にします。`adb devices` で対象端末だけが表示されることを確認し、`<serial>` をその端末のシリアルに置き換えます。ランナーの `--device` 指定だけでは、エージェントが別端末を選ぶことまでは防げません。

全40試行のうち別モデルの2試行では、別端末への操作が確認されています。詳細とモデル比較への影響の限界は評価レポートに記載しています。再測定では、対象端末を1台に限定したことも実行条件として記録します。

```bash
adb devices
export ANDROID_SERIAL="<serial>"

# 正常ビルドの動作と B01 の注入状態を確認（Espresso。Journeys とは独立）
./eval/verify_ground_truth.sh

# 評価ランナーの通し確認（モック。high の clean/B01 を各10回、計20回）
python3 eval/run_matrix.py --dry-run --tiers high --trials 10

# 実機・エミュレータでの実行（high の clean/B01 を各10回、計20回）
python3 eval/run_matrix.py --device "$ANDROID_SERIAL" --tiers high --trials 10 --clean-build
```

`--tiers high` は、本稿で扱ったモデルに限定する指定です。`--trials 10` は、Journey・ビルド・モデルの組み合わせごとに10回実行する指定です。上記のコマンドでは J01 × 2ビルド（clean / B01）× high を対象とするため、各ビルド10回、合計20回になります。`--dry-run` では、実モデルを呼び出さずモックで20回分を処理します。

`--run-id` を省略すると、時刻から実行IDが生成されます。過去の実行IDを指定すると同じ保存先の結果ファイルが上書きされるため、再測定には新しいIDを使います。

実行すると `eval/results/<実行ID>/` に、判定・ステップごとの理由・画面録画・スクリーンショット・logcat が保存されます。本稿の数値と引用は、測定時に保存したこれらの出力に基づいています。生ログ・録画・スクリーンショットは Git 管理対象外で、リポジトリにはソースコード・スクリプト・集計レポートを含めています。
