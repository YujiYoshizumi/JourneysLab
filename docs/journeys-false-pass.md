# Android の Journeys は、バグに気づいたうえで PASS を出すことがある

自然言語で書いた E2E テストを AI エージェントが実行・判定する「Journeys」を、**正解が分かっている環境で20回動かして**、見逃し（False Pass）がどう起きるかを観測した記録です。

結論を先に書くと、壊れているボタンを前にして、エージェントは**別の経路を自分で見つけてゴールに到達し、「不具合の可能性がある」と書き残したうえで PASS と判定しました**。10回中7回です。

---

## 1. Android CLI for Journeys とは何か

Journeys は、テスト手順を自然言語で書いておくと、AI エージェントが画面を見ながら操作し、各ステップの合否を判定してくれる仕組みです。Android Studio の機能として提供されているほか、[Android CLI](https://developer.android.com/tools/agents/android-cli/journeys) 経由で、ターミナルで動く任意のエージェントから実行できます。

テストは XML で書きます。実際に今回使ったファイルの全文です。

```xml
<journey name="J01">
  <description>商品を購入する</description>
  <actions>
    <action>「トートバッグ」をタップする</action>
    <action>「カートに追加」をタップする</action>
    <action>カートを開く</action>
    <action>カートに「トートバッグ」が1点あり、合計が「¥2,200」であることを確認する</action>
    <action>「注文する」をタップする</action>
    <action>「ご注文ありがとうございました」と表示されていることを確認する</action>
  </actions>
</journey>
```

要素は `<journey>` / `<description>` / `<actions>` / `<action>` だけです。ロケータもアサーション API も出てきません。「カートを開く」と書けば、エージェントが画面を見て、どこを押せばカートが開くかを自分で判断します。

### 実行方法について、最初に知っておきたいこと

**Android CLI に Journey 実行専用のサブコマンドはありません。** `android help` を見ても `create` / `run` / `layout` / `screen` / `docs` / `emulator` / `skills` などが並ぶだけで、`android journey run ...` のようなコマンドは存在しません。

実体は「スキル」です。`android init` を実行すると、エージェントの環境に Journeys スキル（`references/journeys.md`）が導入されます。エージェントはそれを読み、`android layout` で画面の構造を取り、`android screen capture` で画面を見て、`adb shell input tap` で操作します。つまり Journeys は**コマンドではなくエージェントの作業手順書**です。

このスキルには判定規則も書かれています。

> A journey succeeds if all elements in the `<actions>` list succeed.

全ステップが成功したときだけ成功。逆に言えば、各ステップの合否をどう決めるかはエージェントの判断に委ねられています。ここが今回の話の起点です。

なお Journey を実行するプロジェクトには Android Gradle Plugin 9.0.0 以上が必要で、Gradle の構成キャッシュを有効にしていると別の Journey が実行されるなどの既知の問題があるため、`org.gradle.configuration-cache=false` を設定しておく必要があります。

## 2. なぜ検証したか

判定するのが AI である以上、下記のような誤判定が起こり得ます。

- **見逃し（False Pass）**: アプリにバグがあるのに PASS と判定される
- **誤検知（False Fail）**: アプリは正常なのに FAIL と判定される

このうち見逃しは、気づかないまま通り過ぎてしまう分だけ厄介です。ただ「見逃すことがある」と言うのは簡単でも、**どういうテストの書き方だと、どの程度の頻度で起きるのか**は、正解が分かっている状態で測らないと言えません。

そこで、仕様どおりに動くビルドと、仕様から1か所だけ外したビルドを用意して、まったく同じ Journey を両方で繰り返し実行しました。本稿はそのうち見逃しに絞って報告します。

## 3. 検証の構成

### 3.1 サンプルアプリ

オフラインの簡易ショップアプリを作りました。ネットワーク通信なし、データはすべてインメモリです。

- 画面は4つ（ホーム／商品詳細／カート／注文完了）
- 商品は4件。スクロールなしで1画面に収まる
- ホーム画面と商品詳細画面には共通のトップバーがある
  - 右上に**カートアイコン**
  - **オーバーフローメニュー**に「カート」「このアプリについて」

**カート画面には2つの経路があります。** トップバーのカートアイコンと、オーバーフローメニューの「カート」です。

### 3.2 注入したバグ

| ID | 仕様からの逸脱 |
|---|---|
| B01 | トップバーのカートアイコンをタップしても何も起きない（ホーム画面・商品詳細画面の両方）。**メニューの「カート」からは従来どおり遷移できる** |

ビルド時に Gradle プロパティで注入します。

```bash
./gradlew :app:assembleDebug                        # 正常ビルド（clean）
./gradlew :app:assembleDebug -Pjourneylab.bugs=B01  # バグ入りビルド
```

バグ ID や注入の有無は、画面にも `contentDescription` にも Logcat にもアプリ名にもバージョン名にも出していません。アプリはログ出力を一切行わず、`applicationId`・アプリ名・`versionName` は両ビルドで同一です。エージェントが画面やログから「このビルドはバグ入りだ」と気づけてしまうと、測っているものが変わってしまうからです。

### 3.3 正解（ground truth）の担保

「見逃し」と言うには、「本当にバグがある」ことを Journeys とは別の手段で保証しなければなりません。ここを省くと、ただの主観になります。

そこで **Journeys とは独立した Espresso のインストゥルメンテーションテスト**を用意しました。

- 正常ビルド向け 11件 — 商品4件がスクロールなしで表示される／**ホームと商品詳細の両方でカートアイコンからカートが開く**／メニュー経由でもカートが開く／カート追加・小計・合計／空カートで「注文する」が無効／注文完了とカートの空化 ほか
- バグ入りビルド向け 3件 — **ホームのカートアイコンが無反応**／**商品詳細のカートアイコンも無反応**／**メニューの「カート」からは遷移できる**

両ビルドともこれらが通ることを確認したうえで、Journeys を走らせています。したがって「B01 ビルドでの J01 の正解は FAIL」と言えます。

### 3.4 なぜ B01 の正解が FAIL なのか

J01 のステップ3は「カートを開く」としか書いていません。ここは意図的です。

この Journey を書いた人は、**ステップ3で「カートアイコンからカートに遷移できること」も確認できるつもりでいる**、という想定を置いています。実際のテストコードでも、こういう「目的だけ書いて手段を書かない」記述はよくあります。その前提に立てば、カートアイコンが壊れている B01 ビルドでは、このテストは落ちてほしい。だから正解は FAIL です。

### 3.5 実行方法と汚染防止

判定を汚染しないよう、次を守っています。

- エージェントには、**ソースコードを含まない作業ディレクトリ**（ビルド済み APK と Journey ファイルだけ）を渡す
- APK のファイル名はランダムな12桁にリネームし、ビルド名との対応表は実行スクリプト側だけが持つ
- エージェントに許可するツールはデバイス操作中心に限定する
- エージェントに渡す指示文は「Journeys スキルに従って実行し、結果を所定の JSON で出力する」だけ。**判定の基準や注意点は一切書かない**（書いた時点で、測っているものが「Journeys の判定」ではなく「その指示文の効果」に変わるため）。全実行で同一のファイルを使い、そのハッシュを結果に記録する

各実行の前に `adb shell pm clear` でアプリのデータを初期化し、判定者とは独立に**画面録画・1.5秒間隔のスクリーンショット・エージェントの出力・logcat** を取得しています。

### 3.6 実行環境

| 項目 | 値 |
|---|---|
| エージェント | Claude Code `2.1.278` |
| モデル | `claude-opus-5` |
| Android CLI | `1.0.16261425` |
| デバイス | エミュレータ Pixel 10 / API 37 / Android 17 / 1080x2424 / `ja-JP` |
| Android Gradle Plugin | `9.4.1` |
| 試行回数 | 正常ビルド10回・バグ入りビルド10回（計20回） |

Journeys はプレビュー段階の機能です。以下の数値はこの環境・この時点での実測値です。

## 4. 結果

| ビルド | 正解 | PASS | FAIL | 判定の一貫性 | 所要（中央値） |
|---|---|---|---|---|---|
| 正常（clean） | PASS | **10** | 0 | 100% | 99秒 |
| バグ入り（B01） | FAIL | **7** | 3 | 70% | 133秒 |

読み取れることは3つあります。

**① 正常なアプリでは、そのまま素直に通る。** 10回中10回 PASS。誤検知はゼロでした。自然言語で書いた6ステップが、毎回そのとおりに実行されています。Journeys の基本的な動作としては期待どおりです。

**② バグ入りビルドでも、10回中7回 PASS になった。** 見逃し率 70%。カートアイコンは壊れていて、Espresso でそれを確認済みなのに、Journey は通ってしまいました。

**③ 同じ条件でも結果がばらつく。** 同じアプリ、同じ Journey、同じモデル、同じ端末で、7回 PASS・3回 FAIL です。**1回実行して PASS だったことは、何も保証しません。** 逆に言えば、検出できる回もあります。

## 5. 何が起きていたか

### 5.1 エージェントの判定理由

見逃した7回の、ステップ3「カートを開く」の判定理由です。エージェントの出力からそのまま引用します。

> ツールバーのカートアイコン（content-desc「カート」）は2回タップしても画面が変わりませんでした。オーバーフローメニューの「カート」項目からはカート画面が開きました。ステップの指示は「カートを開く」だけで開き方の指定がないため合格にしましたが、カートアイコンが反応しないのは不具合と思われます。

> ツールバーのカートアイコン（action_cart）を2回タップしたが、画面は変わらなかった。オーバーフローメニューから「カート」を選ぶとカート画面が開いた。ステップは開き方を指定していないためPASSEDとした。ただし、詳細画面のカートアイコンが反応しない不具合の可能性がある。

> ツールバーのカートアイコン（action_cart）は2回タップしても画面が変わらなかった。オーバーフローメニューの「カート」項目から開いたところ、カート画面が表示された。ステップは開き方を指定していないため PASSED とした。ただしカートアイコンが動かないのはアプリの不具合と思われる。

> ツールバーのカートアイコン（action_cart）は、タップして3秒待っても画面が変わりませんでした（不具合の可能性があります）。オーバーフローメニューの「カート」項目から開いたところ、カート画面が表示されました。ステップには開き方の指定がないため、成功と判定しました。

> カートは開きました。ただし、ツールバーのカートアイコン (action_cart, content-desc「カート」) は2回タップしても反応せず、商品詳細画面のままでした。代わりにオーバーフローメニューの「カート」から開いています。カートアイコンが反応しないのは不具合と思われます。

**エージェントはバグに気づいています。** 気づいたうえで、「ステップに開き方の指定がないから」PASS にしています。これは論理としては筋が通っています。Journey には「カートを開く」としか書いておらず、カートは実際に開いたのですから。

### 5.2 PASS と FAIL を分けたもの

では、残りの3回はなぜ FAIL になったのか。エージェントのセッション記録から、実際にデバイスへ送られた入力操作を全件抜き出して比べました。座標はレイアウトダンプで同定しています（`911,225` がツールバーのカートアイコン、`1027,225` がオーバーフローメニュー、`812,247` がメニュー内の「カート」項目）。

| 判定 | 件数 | 入力操作の並び |
|---|---|---|
| PASS | 7 | 商品カード → カートに追加 → **カートアイコン（1〜2回）** → **オーバーフローメニュー** → メニューの「カート」 → 注文する |
| FAIL | 3 | 商品カード → カートに追加 → **カートアイコン（1〜2回）** → ここで終了 |

10回がきれいに2パターンに分かれました。**違いは「オーバーフローメニューを試したかどうか」だけです。**

FAIL になった3回は、カートアイコンを押し、反応がないので数秒待ち、もう一度確認して、そこで打ち切っています。メニューは一度も開いていません。判定理由も一貫しています。

> ツールバーのカートボタン（resource-id: action_cart、content-desc: 「カート」）を2回タップしたが、カート画面は開かなかった。数秒待ってから layout とスクリーンショットで確認しても、商品詳細画面のままだった。ここでジャーニーの評価を終了した。

つまり見逃しは、エージェントが**バグを見落としたから**起きたのではありません。**ゴールへの別ルートを見つけてしまったから**起きています。そして別ルートを探すかどうかは、実行ごとにぶれます。

### 5.3 自然言語テストの構造的な性質

この挙動は、Journeys の「バグ」ではないと考えたほうが実態に近いはずです。

自然言語で書かれた「カートを開く」を、エージェントは**達成すべきゴール**として解釈します。ゴール指向だからこそ、多少の UI 変更でテストが壊れない柔軟さが得られる。その柔軟さと、「特定の経路が壊れていることを検出する能力」は、同じ性質の裏表です。

ロケータで要素を指定する従来の E2E テストなら、カートアイコンが反応しない時点でテストは必ず落ちます。代わりに、アイコンの ID が変わっただけでも落ちます。Journeys はその逆の性質を持っています。

## 6. 書き手側の対策案

下記、測定結果を踏まえた対策案です。

### 6.1 経路を書く

「カートを開く」ではなく、**手段を明示する**。

```xml
<!-- 検証したい経路が「カートアイコン」なら、そう書く -->
<action>画面右上のカートアイコンをタップする。メニューなど他の経路は使わないこと</action>
<action>タップ直後にカート画面（「合計」の表示がある画面）が表示されていることを確認する</action>
```

「他の経路は使わないこと」と書くこと、迂回が軽減できると思われます。

### 6.2 手段を検証条件に含める

Journeys の公式ドキュメントも「成功条件をステップの一部として書く」ことを勧めています。操作と、その操作の結果として何が起きるべきかを1つのステップに含めると、判定の余地が狭まります。

| 書き方 | 判定の余地 |
|---|---|
| 「カートを開く」 | 広い（どう開いてもよい） |
| 「カートアイコンをタップしてカート画面へ移動し、合計が表示されていることを確認する」 | 狭い |

### 6.3 1回の実行で判断しない

同一条件で 7:3 に割れました。CI に組み込むなら、**複数回実行して多数決を取るか、少なくとも「1回 PASS した」を合格の根拠にしない**運用が要ります。逆に FAIL が出たときも、1回で確定させず再実行の余地を持たせることになります。

### 6.4 判定理由まで読む

今回いちばん実用的かもしれない点です。**見逃した7回すべてで、エージェントは判定理由に「不具合の可能性がある」と書き残していました。**

合否だけを CI のゲートにしていると、この情報は捨てられます。判定理由をログとして保存し、PASS であっても「不具合」「反応しない」といった語が含まれる実行にフラグを立てる、という使い方ができます。

### 6.5 重要な経路は従来型のテストで固定する

「このボタンが機能すること」が要件なら、それは Journeys に委ねるより Espresso などで固定したほうが確実です。Journeys は、画面をまたぐ広い動線を自然言語で手早く覆う用途に向いています。検出したい対象の性質で使い分けるのが現実的です。

## 7. 結論

Journeys が判定しているのは、**ステップに書かれたゴールに到達できたかどうか**です。経路を書かなければ、経路は検証されません。これは仕様どおりの挙動であり、書き手が想定していた検証範囲とのズレが「見逃し」として現れます。

今回の測定で確認できたことをまとめます。

- 正常なアプリに対して、自然言語のテストは安定して通る（10/10）
- 壊れた経路を持つアプリに対しても、別経路が生きていれば通ってしまう（7/10）
- エージェントはバグに気づいていて、判定理由に書き残している
- 同一条件でも判定はばらつく（7:3）
- 見逃しの有無を分けたのは、エージェントが迂回路を試したかどうかだけだった

自然言語で書けることは、書かなくてよいことを意味しません。**何を検証したいのかを言語化する責任は、テストの書き手に残ります。**

### 測定の限界

以下はこの条件での実測値であり、一般化できるものではありません。

- Journey 1本、アプリ1つ、注入したバグ1種、試行20回
- エージェント・モデル・端末・Android CLI のバージョンはいずれも固定。他の組み合わせは測っていない
- Journeys はプレビュー段階の機能で、今後挙動が変わり得る
- 「70%」は、この Journey の書き方に対する値です。書き方を変えれば当然変わります

## 付録: 再現手順

検証に使ったアプリ・Journey・評価ランナーは一式公開しています。

```bash
# 正解の裏付け（Espresso。Journeys とは独立）
ANDROID_SERIAL=<serial> ./eval/verify_ground_truth.sh

# 評価の実行（実行部分をモックにした通し確認）
python3 eval/run_matrix.py --dry-run

# 実機・エミュレータでの実行
python3 eval/run_matrix.py --device <serial> --trials 10 --run-id 20260922-01 --clean-build
```

実行すると `eval/results/<実行ID>/` に、判定・ステップごとの理由・画面録画・スクリーンショット・logcat が保存されます。本稿の数値と引用はすべてこの出力に基づいています。
